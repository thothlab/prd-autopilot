# Фаза 1 — Требования

Запрос — единственный текст во всём процессе, который написал сам пользователь; всё остальное будет твоим изложением. Эта фаза превращает его в артефакт, переживающий любую последующую переформулировку, — чтобы ни одна строка не смогла перестать существовать незаметно.

Работает **до** вопросов брифинга и до сбора контекста. Вопросы уже перекодируют запрос своими словами, поэтому оригинал сохраняется раньше них.

## 1. Гейт редактирования — работает до любой записи

Каждый кусок пользовательского текста — запрос, каждый ответ, каждый вставленный фрагмент — проходит этот гейт по пути в файл, в промпт или на дашборд. Ничто его не обходит.

Ищи:

| Вид | Форма |
|---|---|
| Stripe / OpenAI-подобные | `sk-…`, `sk_live_…`, `sk_test_…`, `rk_live_…`, `pk_live_…` |
| GitHub | `ghp_…`, `gho_…`, `ghs_…`, `github_pat_…` |
| AWS | `AKIA…`, `ASIA…` |
| Google | `AIza…`, `ya29.…` |
| Slack | `xoxb-…`, `xoxp-…`, `xoxa-…` |
| Telegram bot | 8-10 цифр, двоеточие, 35 знаков `[A-Za-z0-9_-]` |
| JWT | `eyJ…`, точка, дальше base64 |
| Строка подключения | `<схема>://<user>:<что-то>@<host>` |
| Приватный ключ | `-----BEGIN … PRIVATE KEY-----` |
| Корпоративное | токен Jira/Confluence, `Bearer …`, cookie сессии, VPN-профиль |
| Общее | ≥32 знаков hex или base64 рядом со словами `key`, `token`, `secret`, `password`, `ключ`, `токен`, `пароль`, `доступ` |

При попадании:

1. Замени значение на `[REDACTED:<VAR_NAME>]`, придумав общепринятое имя переменной для этого провайдера (`STRIPE_SECRET_KEY`, `JIRA_API_TOKEN`, `DATABASE_URL`). Имя — то, что нужно сборке; значение не было нужно никогда.
2. Добавь имя в `.env.example` с пустым значением.
3. Скажи пользователю сразу, одной строкой, простым языком: «Ты прислал токен Jira — я его не сохранил. Впиши сам в `.env`, а этот лучше отзови: он уже побывал в переписке.»
4. Работай дальше. Отредактированный секрет прогон не останавливает.

**Никогда не повторяй значение обратно**, даже чтобы подтвердить, что нашёл. Назвать провайдера достаточно.

Перед первым коммитом прогони этот гейт по всему `prdRoot`. Секрет, попавший туда путём, которого никто не предвидел, всё равно не должен доехать до истории git.

## 2. Записать файл запроса

Отредактированный запрос, **слово в слово**, в `<prdRoot>/prd_XX_brief.md`. Имя файла несёт номер PRD, а дата — frontmatter: каталог PRD переживает не одно сидение, и через месяц приходит «доделай ещё вот это».

```markdown
---
type: brief
title: <название инициативы>
description: <одно предложение>
prd: prd_XX
generated: { by: claude-code/opus-5, at: <ISO 8601 со временем> }
---

# Изначальный запрос

> Записано <дата>. Этот файл не редактируется — он эталон, с которым
> сверяется готовый результат.

<весь текст пользователя, дословно, после редактирования секретов>
```

Frontmatter — vault-режим; в local-режиме он не нужен, но и не мешает. Формат ключей принадлежит скиллу `vault-reporting`, если он установлен; его нет — хватит показанных.

Правила, ради которых этот файл вообще существует:

- **Никакого пересказа, вычистки и перестановки.** Плохая грамматика, противоречия, обрывки фраз и повторы остаются. Приглаженный запрос — это уже PRD, а PRD как раз то, с чем нельзя сверяться.
- **Запросом считается всё** — идея, отступления, ограничения, «и ещё хорошо бы», предпочтения по стеку, срок, брошенный вскользь, номер тикета Jira.
- **Больше не редактируется.** Мысли того же сидения дописываются под `## Дополнения`, с датой, и не сливаются с исходным текстом. Запрос, надиктованный **в другой день**, — это новый PRD со своим номером; дописать его к старому значит стереть тот факт, что работу заказали дважды.
- **Путь к файлу записывается в `state.js` как `briefFile`**, чтобы ниже по течению его не приходилось угадывать.

## 3. Разобрать на требования

Раздели запрос на наименьшие единицы, которые могут независимо быть истинными или ложными про готовый результат. Пиши `<prdRoot>/prd_XX_manifest.md`.

Каждое требование — строка, и каждая строка несёт **точные слова, из которых она взялась**. Цитата и есть суть: пересказанное требование уплывает ровно так же, как пересказанный запрос.

```markdown
---
type: manifest
title: Манифест требований — <название>
prd: prd_XX
generated: { by: claude-code/opus-5, at: <ISO 8601> }
---

# Манифест требований

Источник: `prd_XX_brief.md`. Строку из этого списка может снять **только пользователь**.

| ID | Из запроса (дословно) | Статус | Основание | Где |
|----|----------------------|--------|-----------|-----|
| R01 | «форма перевода по номеру телефона» | in-ticket | — | PRD §Data model → задача 02 |
| R02 | «список последних получателей» | in-ticket | — | PRD §API list → задача 04 |
| R03 | «чтобы работало и на iOS» | in-spec | — | спек-дельта `transfer/spec.md` §ADDED |
| R04 | «и пуш после успешного перевода» | dropped | пользователь: «пуши не надо, только экран успеха» | — |
| R05 | «в фирменных цветах» | placeholder | токены дизайна не переданы | отчёт |
| R06i | *(подразумевается)* нужен экран ошибки перевода | deferred | Вне рамок §3: в запросе его не было | отчёт |
```

### Статусы

| Статус | Значение | Кто вправе поставить |
|---|---|---|
| `open` | ещё нигде не решено | начальное состояние |
| `in-spec` | легло в PRD или спек-дельту, раздел записан | ты |
| `in-ticket` | есть задача, которая это доставляет | ты |
| `done` | сделано и отревьюено, коммит записан | ты |
| `placeholder` | в работе, но на месте пользовательского факта стоит заглушка | ты |
| `deferred` | сознательно отложено, лежит во «Вне рамок» с причиной | ты |
| `dropped` | **отменено пользователем** | **только пользователь** |

Ради трёх правил ниже файл и существует:

- **Статус `dropped` не ставится без цитаты.** В «Основании» лежат слова пользователя, которыми он это отменил. Нет слов — нет отмены; предложить снять требование ты вправе, но это вопрос в брифинге, а не смена статуса своей рукой.
- **Отложить и отменить — разные действия.** Отложить решаешь ты, отменить — только он. Каждая отложенная строка появляется в итоговом отчёте под «что не вошло», чтобы пользователь узнал о ней, пока работа ещё свежа, а не через месяц.
- **Молчание ничего не отменяет.** Требование, о котором перестали упоминать, остаётся живым. Забыть и решить не должны выглядеть на бумаге одинаково — иначе через два дня их будет не различить.

### Подразумеваемые требования

Помечай хвостовой `i` (`R06i`) всё, что запрос явно *подразумевает*, но не говорит: «форма перевода» подразумевает состояние ошибки и подтверждение; «список получателей» подразумевает, откуда он берётся и что показывать, когда он пуст.

Строки этого сорта топят инициативу чаще прочих: они слишком очевидны, чтобы их проговаривать, и слишком велики, чтобы их не заметить в конце. Их место — вопросы брифинга; выдумывать за пользователя или молча пропускать одинаково плохо. В режиме **full** каждая превращается в помеченное решение `ASSUMPTION` и попадает в итоговый отчёт.

### Открытые находкой ограничения

Помечай `D` (`D01`, `D02`) всё, что **сборка** доказала, а план не знал: модель данных, которая не держит; предполагаемый контракт бэка, которого нет; два требования, которые на практике сталкиваются. Основание — сама находка, и она называет требование, которому служит.

Строка `D##` — единственное, что вправе войти в манифест после брифинга, и только из `phases/5-repair.md`. Это не требование пользователя и оно никогда не заменяет требование: то, что код доказал невозможным, — вопрос к пользователю, а не `D##`, тихо отправляющий требование на покой. Идея, пришедшая по ходу работы, тоже не находка — это `A##`, и живёт она в PRD по обычным правилам родителя и пропорции.

### Насколько мелко резать

Одно требование = одна вещь, которая может независимо быть истинной или ложной.

- «форма перевода по номеру и список последних получателей» → **два** требования. Одно может работать, пока другое нет.
- «чтобы выглядело по гайдам» → **одно**, и оно непроверяемо по своей природе: пометь и дай брифингу превратить его в проверяемое либо оставь как зафиксированный вопрос вкуса.
- Инициатива на страницу текста обычно даёт 15-40 строк. Меньше десяти из длинного запроса значит, что ты пересказал, а не разобрал — переделай.

**Номер тикета трекера — не требование, а источник.** Ключ Jira в запросе означает, что в Фазе 2 его надо прочитать; сам по себе он ничего не описывает. Требования выйдут из его содержимого, каждое со своей цитатой.

## 4. Отчитаться одной строкой

«Разобрал инициативу на 23 требования — дальше слежу, чтобы ни одно не потерялось.» Таблица в чат не выводится: артефактом является файл, а в чате остаётся упоминание, что он есть.

## Гейты

Записаны здесь, потому что все они читают этот файл. Провал гейта — не предупреждение, фаза переделывается.

**G1 — после брифинга.** У каждого требования есть статус. Всё, что осталось `open`, имеет записанную причину. В режиме **full** `open` не остаётся ничего: самобрифинг отвечает на всё либо помечает `placeholder`.

**G2 — после PRD и спек-дельт.** Две половины, обе обязательны, по `phases/3-prd.md`.

- *Твой собственный проход* — ноль `open`. Каждое живое требование `in-spec`, `deferred` или `dropped`, с записанным разделом. **Строка `open` означает, что PRD неполон** — переписывай PRD, а не иди дальше.
- *Независимый проход* — субагент получает запрос и PRD со спек-дельтами и **не получает** этот файл; он докладывает, чего PRD не покрывает. PRD писал ты, поэтому ты не видишь того, чего не написал; этот файл делает потерю находимой, но не делает тебя тем, кто её найдёт.

**G3 — после плана.** Оба направления обязательны:

- *Вперёд* — каждое `in-spec`-требование ложится хотя бы в одну задачу. Требование без задачи сделано не будет.
- *Назад* — каждая задача возводится хотя бы к одному требованию или к решению PRD, которое само возводится к требованию. **Задача, не возводящаяся ни к чему, — работа, которую никто не заказывал**: вырежь её или привяжи к тому, чему она на самом деле служит.

**G4 — в финальной фазе.** Слепая приёмка по `phases/8-final.md`. Каждое расхождение между манифестом и слепым вердиктом идёт в отчёт.

## Поддержание

Манифест обновляется ровно в пяти местах, а не непрерывно:

| Когда | Что меняется |
|---|---|
| после каждого ответа брифинга | `open` → `dropped` / уточнено / подтверждено |
| после того, как написаны PRD и дельты | `open` → `in-spec` / `deferred`, раздел записан |
| после нарезки задач | `in-spec` → `in-ticket`, номер задачи записан |
| после того, как задача села | `in-ticket` → `done` / `placeholder`, коммит записан |
| когда сборка противоречит плану | новая строка `D##`, затронутые строки перенаправлены на исправленный раздел |

Обновление — это правка затронутых строк, а не перезапись таблицы целиком. Она живёт дольше любого контекста и меняется точечно: обращайся с ней как с данными, а не как с текстом, который можно переписать заново.
