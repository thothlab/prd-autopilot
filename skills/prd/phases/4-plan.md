# Фаза 4 — План задач

Разрезать PRD и спек-дельты на единицы работы, каждую из которых сделает свой субагент в своём свежем контексте.

Прежде чем что-то резать, пойми, сколько стоит разрез.

## Цена границы

Каждая граница задачи — это свежий контекст, влетающий из ниоткуда: прочитать интерфейсы, изучить код, найти команду тестов — 20-40 тысяч токенов на въезд, до того как написана строка, плюс ревью в конце. Значит, задачу стоит заводить, **только когда работы внутри больше, чем стоит её собственная граница**; задача, несущая восемьдесят слов инструкции, платит полную цену и отдаёт долю ценности.

Ошибка, которой стоит избегать, не очевидная. Резать слишком мелко *ощущается* аккуратностью и является обратным: каждая лишняя граница — ещё один шанс двум субагентам разойтись во мнении об интерфейсе и ещё один контекст, потраченный на переучивание проекта. **Меньше и плотнее лучше, чем больше и тоньше** — всегда.

## Бюджет яруса

Определи ярус по **тому, что надо сделать**, потом режь под него. Назови ярус и число задач одной строкой пользователю.

| Ярус | Как выглядит инициатива | Задач |
|---|---|---|
| **T0** | одна поверхность, один слой, без внешних контрактов — правка в знакомом модуле, один экран поверх существующих данных, живая спека домена уже есть | **нет — делается из PRD за один заход** |
| **T1** | одна связная фича: несколько поверхностей над одной формой данных, максимум один внешний контракт | 2-3 |
| **T2** | несколько фич, или одна фича сквозь несколько слоёв — данные, логика, интерфейс, интеграция | 4-8 |
| **T3** | ≥ 3 действительно независимых подсистемы или домена, у каждого свои данные и своя причина меняться | 9-16 |
| **>16** | — | **нельзя.** Либо обоснуй строкой в PRD, либо разбей на два PRD |

**Ярус читается из работы, а не из длины PRD.** Глубина решает, насколько тщательно расписано каждое требование; про объём работы она не говорит ничего. `deep`-PRD на одну форму — это длинный документ про одну форму: всё ещё T0, всё ещё один контекст, всё ещё без задач.

**T0 существует и встречается часто.** Правка в одном модуле, один экран, миграция вызовов в одном пакете — не режь, сделай за один заход, отревьюй один раз, готово. Пропуск нарезки здесь не срезание угла; заводить задачи было бы тратой. Скажи прямо: «Инициатива небольшая — делаю сразу, без разбивки на задачи».

На T0 этап `plan` в `state.js` помечается `skipped` с причиной в примечании — «ярус T0 — без разбивки на задачи», — а не остаётся `pending`. Этап, который никуда не движется, читается как застрявшая работа.

Переход на ярус выше требует причины, записанной в PRD, а не ощущения.

## Как резать

Каждая задача — **узкий, но полный путь через все слои**, которых касается: данные, логика, интерфейс, тесты. Не горизонтальный срез одного слоя. Когда она сделана, работает end-to-end что-то, чего не работало раньше, и это можно показать.

- Всё, что должно существовать раньше остального — каркас, общие примитивы, схема, — это задача 01, одна. С ней не параллелится ничего.
- Подготовительная работа, которая делает следующие задачи лёгкими, идёт раньше. Сделай изменение лёгким, потом сделай лёгкое изменение.
- Дай каждой задаче её **блокирующие рёбра** — задачи, которые должны закончиться раньше. Нет блокеров — можно стартовать сразу.
- Нумеруй с `01` в порядке зависимостей, блокеры первыми.
- **Задачи, закрывающие требования `R`, идут раньше задач, закрывающих только `A`.** Если прогон оборвётся, недостающим окажется твоё добавление, а не просьба пользователя.

**Исключение — широкий механический рефактор** (переименование символа через весь код, миграция API). Вертикально его не нарезать: делай expand → миграция вызовов пачками по модулям, каждая пачка своя задача → contract удалением старой формы. Ярус тут читается по числу пачек, а не по числу фич.

## Пол — две проверки, которые проходит каждая задача

**Проверка окупаемости.** Её субагент потратит на въезд больше, чем на работу? Тогда это не задача. Слей с соседкой, от которой она зависит.

**Проверка соседства.** Меньше трёх критериев приёмки, трогает те же файлы, что соседняя задача, и не отделена от неё границей волны? Тогда это пункт чеклиста внутри соседки, а не своя задача.

## Проход слияния — обязательный

После черновика, до записи файлов, пройди список ещё раз и слей:

- соседние задачи, трогающие одни файлы, между которыми нет волны;
- любую задачу меньше трёх критериев приёмки, у которой есть естественный родитель;
- цепочки, где B заблокирована A, больше A никого не блокирует, и A сама по себе ничего не показывает.

Потом перепроверь ярус. Черновик, приземлившийся на 14 и слившийся до 7, был T2, притворявшимся T3, — нормально, ради этого проход и существует.

## Волны — что может лететь вместе

Блокирующие рёбра говорят, что ещё нельзя начать. **Волны говорят, что можно начать одновременно**, и считать их не опционально: без волн команда летит по одной задаче за раз, и план, задачи которого действительно независимы, занимает вдвое-втрое больше без всякой причины.

Посчитай один раз, сразу после прохода слияния, из двух вещей, которые у тебя уже есть:

1. **`волна = 1 + max(волна её блокеров)`** — всё без блокеров это волна 1.
2. **Потом раздели каждую волну по зонам.** Две задачи одной волны, которые писали бы одни файлы, вместе идти не могут: сдвинь позднюю в следующую волну. Одни файлы → строго по очереди, всегда. Два субагента, правящие один файл, перезаписывают друг друга, и потеря молчаливая.

Для второго шага каждая задача называет свою зону:

**Зона:** `features/transfer/` · `core/network/`

Каталоги и модули — граница владения, а не список файлов. Это единственное исключение из «избегай путей»: здесь путь *и есть* принимаемое решение.

**Ещё одно ограничение, которое не видно из графа зависимостей: общий тулчейн.** В Gradle-, KMP-, Xcode- и подобных репозиториях верификация (`./gradlew` для Android, сборка iOS, ktlint, detekt) выполняется **последовательно**, даже если сами задачи параллельны: одновременные таски одного проекта конфликтуют за блокировки и кэш. Проще держать такие задачи серийными, чем ловить плавающие падения. Это записывается в `prd_XX_interfaces.md` как правило проекта, а не помнится.

Волна из одной задачи — нормальный ответ. Задача 01 по определению своя волна.

**Не производи параллельность искусственно.** Разрезать задачу надвое, чтобы волна выглядела шире, — потратить два контекста ради экономии одного, и проход слияния существует, чтобы это отменять. Волны *обнаруживаются* в графе зависимостей, а не проектируются в него.

**Номер волны присваивается один раз, здесь, и потом не пересчитывается.** Он описывает план, а не фронтир: когда задача закончилась и следующая стала запускаемой, это работа идёт по плану, а не план меняется. Перенумерация по ходу заставляет строки прыгать между группами на дашборде, и пользователь читает это как потерю плана.

Пиши `wave` в каждый файл задачи и в `state.js`.

## Засеять interfaces.md — до того, как полетит первая задача

Фаза 3 решила границы: что каждая единица владеет, что выставляет, что прячет. **Скопируй этот раздел в `<prdRoot>/prd_XX_interfaces.md` сейчас**, под заголовок «Границы, решённые в PRD», вместе с правилами проекта, которые субагент вывести не может: стек и версии, команды запуска и тестов, что трогать запрещено, правило последовательной верификации из раздела волн и правило «не хватает зависимости — не добавляй сам, верни `BLOCKED` с названием».

Это копирование, а не проектирование. Превращается в проектирование — значит, Фаза 3 оставила границы нерешёнными, и правильный ход вернуться и решить их, а не изобретать здесь, где план уже нарезан вокруг них.

Почему нельзя дождаться возврата задачи 01: первый субагент читает этот файл до того, как что-то напишет, и прочитанное — единственное, что стоит между ним и изобретением собственной версии каждой границы.

На ярусе T0 контекст один и волн нет, поэтому файл получает правила проекта и швы, и больше ничего. Он всё равно пишется: Фаза 5 сверяет свою работу с этими швами, а Фаза 9 сворачивает его в память проекта.

## Файлы задач

```markdown
---
type: task
title: <название задачи>
prd: prd_XX
task: NN
task_status: pending
generated: { by: claude-code/opus-5, at: <ISO 8601> }
---

# Задача 03 — Форма перевода: ввод номера и суммы

**Требования:** R01, R01.1, A01
**Блокируется:** 01, 02
**Зона:** `features/transfer/`
**Волна:** 2

## Цель

Что должно заработать, простым языком. Клиент открывает форму, вводит номер
и сумму, видит имя получателя и подтверждает. Обрыв на середине не теряет
введённое, отказ бэка показывается текстом, а не молчанием.

## Из запроса, дословно

> «форма перевода по номеру телефона»
> «чтобы было понятно, кому уходит»

## Разделы PRD и спек

PRD: Истории 1-3, Решения §2, Границы §1.
Спек-дельта `transfer/spec.md`: Requirement «Transfer by phone», сценарии 1-4.

## Рамки

Что в задачу входит и что явно нет — соседние задачи, которых она не трогает.

## Подзадачи

1. …
2. …

## Что на выходе

Конкретные артефакты: экран, модель, контракт, тест.

## Definition of Done

- [ ] Форма из трёх полей доходит до подтверждения
- [ ] Имя получателя показано до подтверждения
- [ ] Прерванный ввод восстанавливается, а не сбрасывается
- [ ] Отказ бэка даёт понятный текст, а не падение
- [ ] `./gradlew :feature:transfer:test` зелёный
- [ ] ktlint и detekt чистые

## Тесты

Проверки, привязанные к конкретным Scenario спек-дельты: какой сценарий
каким тестом закрыт и на каком шве он стоит.
```

Дословные цитаты из запроса не украшение. Это последнее, что стоит между свежим контекстом и правдоподобной переинтерпретацией заказанного, и стоят они около сорока токенов.

Избегай путей к файлам и кусков кода: они устаревают быстрее задачи. Исключение — структура, которую проза передаёт хуже кода (схема, конечный автомат, форма типа). Тогда вставляй только её.

**Отчёт по задаче** (`prd_XX_rep_NN_<slug>.md`) пишется не здесь, а в Фазе 5, когда задача сделана.

## Гейт G3 — перед публикацией

**Вперёд:** каждое `in-spec`-требование появляется в строке «Требования» хотя бы одной задачи. Требование, которого нет ни в одной задаче, сделано не будет.

**Назад:** каждая задача называет хотя бы одно требование или решение PRD, которое само возводится к требованию. **Задача, не возводящаяся ни к чему, — работа, которую никто не заказывал.**

**Полнота:** у каждой задачи есть зона и волна, никакие две задачи одной волны не делят зону, и **`prd_XX_interfaces.md` уже несёт границы из PRD**. Отсутствующая волна означает, что Фазе 5 придётся угадывать порядок, и она угадает «по одной»; пустой `interfaces.md` означает, что архитектуру угадает первый субагент.

Потом обнови манифест: `in-spec` → `in-ticket`, с номером задачи.

## Опубликовать план в приборы

В момент, когда файлы задач существуют, **каждая задача уходит в `state.js` и на дашборд** — не когда стартует первая, не после того, как сядет первая:

```json
{ "id": "04", "title": "Список последних получателей", "requirements": ["R02", "R02.1"],
  "blockedBy": ["02"], "wave": 3, "zone": ["features/transfer/recent/"], "status": "pending",
  "retries": 0, "repairs": 0, "handoffs": 0 }
```

`status: "pending"`, без отметок времени — они появятся при запуске. Три счётчика стартуют с нуля **здесь**, а не при первом использовании: поле, созданное на середине прогона, — это поле, которое кто-то инкрементит из `undefined`, и получившийся `NaN` на дашборде никто никогда не увидит.

**Работа, идущая при дашборде, который всё ещё пишет «задачи не нарезаны», — сломанные приборы**, и ломаются они ровно в тот момент, когда пользователь скорее всего посмотрит. Счётчик, волны, блок хода работы и честная шкала прогресса читаются из этого массива. См. `phases/7-instruments.md`.

## Планировочный отчёт и коммит документов

Когда файлы задач написаны, напиши `<prdRoot>/prd_XX_rep_00_<slug>.md` (`type: report`). Это срез планирования — то, что человек откроет через месяц, когда `state.js` уже ничего не скажет:

- **Что спланировано** — инициатива в трёх строках и ярус с числом задач;
- **Какие файлы произведены** — PRD, спек-дельты по доменам, задачи;
- **Затронутые домены** — какие живые спеки изменятся на архивировании;
- **Открытые места** — каждый `PLACEHOLDER` из PRD, по строке;
- **Отклонения** — всё, что расходится с изначальным запросом, и почему;
- **Дальше** — первая задача.

В vault-режиме дополни `index.md` бандла инициативы (`type: index`) ссылками на PRD, задачи, спек-дельты и этот отчёт: это точка входа во весь бандл, и она устаревает первой. Нет `index.md` — заведи.

Потом закоммить документы в репозиторий vault — это первый из трёх коммитов vault за прогон:

```bash
git -C "$vault" add "Projects/<project>/<initiative>/"
git -C "$vault" commit -m "prd-XX: планирование закончено — <slug>"
git -C "$vault" push
```

В local-режиме документы лежат в `.prd/` кодового репозитория и уходят в первый же коммит задачи; отдельного коммита документов там нет.

## Как показывать план

Сначала файлы. **Задача, существующая только в диалоге, — не задача**: пользователь видит сводку по тому, что уже лежит на диске.

**Параллельность — одна строка, и только если она правда**: «Часть задач пойдёт параллельно — 6 задач в 4 волны». Это единственный кусок процесса, который пользователь реально чувствует, потому что он меняет время ожидания. Никогда не заявляй её для плана, который одна длинная цепочка.

**semi и interview** — один экран, простым языком, без технических деталей, по строке на задачу: что пользователь сможет, когда она сядет. Потом: «Показываю план и начинаю. Скажи "стоп", если что-то не так». И начинай. Не жди одобрения — ожидание и есть тот отказ, ради устранения которого скилл переписан. **Никогда не обещай отсчёт:** держать паузу ты не умеешь, поэтому названная задержка — обещание, которое ты нарушишь.

`interview` здесь — это `semi`, и намеренно: смыслом того режима были вопросы, а не список задач. Пользователь, который хочет спорить о нарезке, сказал «ручной режим», а это другое слово.

**full** — тот же экран как уведомление. Без паузы.

**manual** — план это гейт. Показать с технической детализацией, обсудить нарезку и порядок, править по просьбе, ждать явного «ок». Фаза 5 стартует только по согласованным задачам.
