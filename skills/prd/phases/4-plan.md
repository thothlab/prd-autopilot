# Фаза 4 — План задач

Разрезать PRD и спек-дельты на единицы работы, каждую из которых сделает отдельный субагент в собственном свежем контексте.

Прежде чем резать, прикинь, во что обходится сам разрез.

## Сколько стоит граница

За каждой границей стоит контекст, который начинает с нуля: читает интерфейсы, разбирается в коде, выясняет команду тестов. Двадцать-сорок тысяч токенов уходит на въезд, до того как появится первая строка кода, плюс ревью в конце. Значит, заводить задачу стоит **только тогда, когда работы внутри больше, чем стоит её граница**. Задача на восемьдесят слов инструкции платит полную цену и возвращает малую долю.

Ошибка, которой стоит бояться, не та, что кажется. Мелкая нарезка ощущается предусмотрительной и таковой не является: каждая лишняя граница — ещё одна пара субагентов, которым предстоит разойтись во мнении об интерфейсе, и ещё один контекст, потраченный на изучение того же проекта. **Крупнее и плотнее выигрывает у мельче и тоньше** практически всегда.

## Ярусы

Ярус определяется по тому, **что предстоит сделать**, и уже под него режется план. Назови ярус и число задач одной строкой пользователю.

| Ярус | Как выглядит инициатива | Задач |
|---|---|---|
| **T0** | одна поверхность, один слой, без внешних контрактов: правка в знакомом модуле, экран поверх готовых данных, живая спека домена уже есть | **нет — делается из PRD за один заход** |
| **T1** | одна связная фича: несколько поверхностей над одной формой данных, максимум один внешний контракт | 2-3 |
| **T2** | несколько фич или одна фича, проходящая через несколько слоёв — данные, логика, интерфейс, интеграция | 4-8 |
| **T3** | три и больше действительно независимых подсистем или доменов, у каждого свои данные и своя причина меняться | 9-16 |
| **>16** | — | **нельзя.** Либо обоснуй строкой в PRD, либо раздели на два PRD |

**Ярус читается по объёму работы, а не по объёму документа.** Глубина решает, насколько подробно расписано каждое требование, и ничего не говорит о том, сколько предстоит построить. Подробный PRD на одну форму остаётся длинным текстом про одну форму: ярус T0, один контекст, ноль задач. Считать задачи по длине PRD — значит превратить ручку глубины в множитель работы, то есть ровно наоборот тому, зачем она есть.

**T0 — не вырожденный случай, а частый.** Правка в одном модуле, один экран, миграция вызовов внутри пакета: не режь, сделай за заход, отревьюй один раз, закрой. Заводить здесь задачи — трата, а не страховка. Скажи прямо: «Инициатива небольшая — делаю сразу, без разбивки на задачи».

При этом этап `plan` в `state.js` помечается `skipped` с причиной в примечании («ярус T0 — без разбивки на задачи»), а не остаётся `pending`: этап, который никуда не движется, читается пользователем как застрявшая работа.

Переход на ярус выше нуждается в причине, записанной в PRD.

## Как резать

Задача — это **узкий, но сквозной путь через все слои, которых она касается**: данные, логика, интерфейс, тесты. Не горизонтальный срез одного слоя. Признак правильного разреза: когда задача сделана, работает то, чего не работало раньше, и это можно показать.

- Всё, что должно существовать раньше остального — каркас, общие примитивы, схема, — это задача 01. Она идёт одна.
- Подготовка, которая делает следующие задачи простыми, идёт раньше них.
- У каждой задачи есть блокирующие рёбра — задачи, обязанные завершиться раньше. Нет блокеров — можно стартовать сразу.
- Нумерация с `01`, в порядке зависимостей, блокеры первыми.
- **Задачи, закрывающие требования пользователя, идут раньше задач, закрывающих только твои добавления.** Оборвётся прогон — недостающим окажется добавленное тобой, а не заказанное им.

**Широкий механический рефактор — исключение.** Переименование символа через весь код или миграция API вертикально не режется. Схема другая: expand, затем миграция вызовов пачками по модулям (каждая пачка — задача), затем contract удалением старой формы. Ярус здесь считается по числу пачек.

## Первая волна упирается в проходимый путь

**Разрез по слоям откладывает первую видимую вещь на весь прогон, и это самый дорогой из известных способов ошибиться.** Фундамент, контракты, сущности, хранилище медиа, обмен сообщениями — каждая такая задача закрывается зелёной и правильной, а показать после всей волны нечего. Пользователь просит стенд на второй день; приемлемого стенда нет ни на пятый, ни на седьмой.

Замер. Прогон, нарезанный по слоям, закрыл пакет из двадцати двух задач с полутора тысячами зелёных тестов — и сквозной сценарий рвался в трёх местах. Следующий пакет пришлось нарезать заново, теперь по путям пользователя: поиск, категории, размещение, сообщение продавцу, избранное, кабинет, страница продавца. **Это тот же продукт, разрезанный второй раз, потому что первый разрез отвечал на вопрос «из чего он состоит», а не на вопрос «что можно показать».**

Отсюда обязанность плана:

- **Первая волна заканчивается одним сквозным путём, пройденным целиком** — от входа пользователя до результата, который он видит. Один путь, самый короткий из ценных. Не «фундамент готов», а «гость открывает главную, ищет словом, открывает карточку».
- **Слои строятся внутри этого пути, а не до него.** Схема, контракт и хранилище появляются в том объёме, которого требует первый путь, и дорастают следующими путями. Задача 01 остаётся каркасом — но каркасом ровно под первый путь, а не под всю систему.
- **Остальные пути идут отдельными задачами, каждая — снова сквозная.** Это и есть тот разрез, к которому прогон приходит переделкой, если не начал с него.
- **Путь, который нельзя пройти руками, готовым не считается**, каким бы зелёным ни был набор.

**Возражение «сначала надо построить основание, иначе всё переделывать» звучит убедительно и почти всегда неверно.** Основание, выведенное из одного настоящего пути, оказывается ближе к нужному, чем основание, выведенное из представления о системе целиком: первое проверено работой, второе — рассуждением. Переделка бывает и в том, и в другом случае, но в первом она видна на третий день, а не на седьмой.

## Адрес, на котором смотрит заказчик

**Если у прогона есть стенд — назови его в плане один раз, и дальше он входит в критерии приёмки каждой задачи с видимой поверхностью.** Стенд — это адрес, куда смотрит человек: развёрнутый URL, приложение на устройстве, запущенная сборка. Он появляется в `state.js` рядом с `prdRoot` и уезжает вниз в теле задачи.

Без этого исполнитель поднимает свою сборку на своём порту, закрывает на ней критерии, возвращает `DONE` — и он прав, потому что о другом адресе ему не сказали. Замер того же прогона: задача на 247 тысяч токенов вернулась с оговоркой «стенду заказчика фотографии ещё не видны». Работа сделана, доставки нет, и обнаружилось это, когда пользователь открыл страницу сам.

**Стенд обновляется по завершении волны, а не в конце прогона.** Это дешевле любой альтернативы: расхождение между «работает у исполнителя» и «работает у заказчика» ловится на одной волне, а не на двадцати задачах разом.

## Два условия, которым обязана удовлетворять задача

**Окупаемость.** Если субагент потратит на въезд больше, чем на работу, это не задача — слей её с той, от которой она зависит.

**Отдельность.** Меньше трёх критериев приёмки, те же файлы, что у соседки, и никакой волны между ними — значит, это пункт чеклиста внутри соседки, а не самостоятельная задача.

**Размер.** Задача режется так, чтобы уложиться примерно в полсотни вызовов инструментов — тот же потолок, который назначен исполнителю в `prompts/executor.md`. Это не третье условие, а мера первых двух: окупаемость снизу, потолок сверху. Прикидывай по числу файлов, которые придётся прочитать и тронуть, и по тому, сколько раз предстоит прогнать проверки.

**Прошлые прогоны говорят, попадаешь ли ты в этот размер.** В `state.js` закрытых PRD у задач есть поле `calls` — сколько вызовов исполнитель потратил на самом деле. То же самое, но по транскриптам и без участия скилла, считает `tools/prd_cost.py ceiling` — он лежит в корне репозитория prd-autopilot, в установленном скилле его нет; нужен `python3`. Им проверяют прогоны, где `calls` не заполняли. Задачи, стабильно возвращающие вдвое больше потолка, означают, что режут крупно, и следующий план надо резать мельче — сами по себе исполнители аккуратнее не станут.

**Замер, по которому калибруются эти слова.** Прогон на 37 исполнителях: медиана 95 вызовов при потолке 50, за потолком 81% задач и 96% денег, ушедших на исполнителей. Медиана вдвое выше потолка — это утверждение не про исполнителей, а про разрез: задачи задуманы вдвое крупнее, чем объявлено, и чинится это здесь, делением надвое, а не увещеванием того, кто их исполняет. Пока медиана держится около потолка, разрез верен; ушла к двум потолкам — режь мельче на следующем прогоне. Обратное тоже читается: задачи по десять вызовов — это пункты чеклиста, которым выдали по контексту, и проход слияния ниже должен был их схлопнуть.

## Обязательный проход слияния

Черновик готов — пройди список ещё раз, до записи файлов, и слей:

- соседние задачи в одних файлах, между которыми нет волны;
- задачи короче трёх критериев приёмки, у которых есть естественный родитель;
- цепочки, где B заблокирована A, больше A никого не блокирует, а сама A ничего не показывает.

Потом пересчитай ярус. Черновик, начавшийся с четырнадцати задач и схлопнувшийся до семи, был T2, притворявшимся T3, — это нормальный исход, ради него проход и существует.

## Волны

Блокирующие рёбра говорят, что ещё нельзя начинать. **Волны говорят, что можно начать одновременно**, и считать их обязательно: без волн работа идёт по одной задаче, и план, задачи которого на самом деле независимы, растягивается вдвое-втрое без всякой причины.

Считаются они один раз, сразу после слияния, из того, что уже есть:

1. **`волна = 1 + max(волна блокеров)`**; всё без блокеров — волна 1.
2. **Затем каждая волна делится по зонам.** Две задачи одной волны, которые писали бы одни и те же файлы, вместе идти не могут: поздняя уезжает в следующую волну. Общие файлы означают очередь всегда — два субагента, правящих один файл, затирают друг друга, и потеря происходит молча.

Для второго шага каждая задача объявляет зону:

**Зона:** `features/favorites/` · `core/network/`

Это каталоги и модули, то есть граница владения, а не перечень файлов. Единственное место, где путь уместен: здесь путь и есть принимаемое решение.

**Есть второе ограничение, невидимое в графе зависимостей, — общий тулчейн.** В Gradle-, KMP- и Xcode-репозиториях проверки (сборка Android, сборка iOS, ktlint, detekt) идут **по очереди**, даже когда сами задачи параллельны: одновременные таски одного проекта дерутся за блокировки и кэш и дают падения, которых нет в коде. Записывается это в `prd_XX_interfaces.md` как правило проекта, а не держится в голове.

Волна из одной задачи — нормальный ответ, а задача 01 по определению одна в своей волне.

**Не создавай параллельность искусственно.** Разрезанная надвое задача, чтобы волна казалась шире, тратит два контекста ради экономии одного — именно это отменяет проход слияния. Волны находят в готовом графе зависимостей, а не закладывают в него. Если всё зависит от всего, правильный ответ — N волн по одной задаче, и так и надо сказать.

**Номер волны присваивается здесь один раз и потом не пересчитывается.** Он описывает план, а не текущий фронт работ: когда задача закончилась и следующая стала запускаемой, это движение по плану, а не изменение плана. Перенумерация заставит строки прыгать между группами на дашборде, а пользователь, который не знает, что номера переписали, прочитает это как потерю плана.

## Засеять interfaces.md — до первой задачи

Фаза 3 решила границы: чем владеет каждая единица, что выставляет наружу, что прячет. **Перенеси этот раздел в `<prdRoot>/prd_XX_interfaces.md` сейчас**, под заголовок «Границы, решённые в PRD», вместе с правилами проекта, которые субагент вывести не сможет: стек и версии, команды сборки, тестов и линтеров, что трогать запрещено, правило последовательных проверок и запрет самостоятельно подключать зависимости.

Это перенос, а не проектирование. Если получается проектирование — значит, Фаза 3 оставила границы нерешёнными, и правильный ход вернуться и решить их там, а не изобретать здесь, где план уже нарезан вокруг них.

Ждать возврата задачи 01 нельзя: первый субагент читает этот файл до того, как что-то напишет, и прочитанное — единственное, что отделяет его от изобретения собственной версии каждой границы.

На ярусе T0 контекст один и волн нет, поэтому файл получает правила проекта и швы — и всё. Он всё равно пишется: Фаза 5 сверяется с этими швами, а Фаза 9 сворачивает файл в память проекта.

## Файлы задач

```markdown
---
type: task
title: <название задачи>
prd: prd_XX
task: NN
task_status: pending
generated: { by: claude-code/opus-5, at: <ISO 8601> }
---

# Задача 03 — Избранное: кнопка на карточке

**Требования:** R01, R01.1, A01
**Блокируется:** 01, 02
**Зона:** `features/favorites/`
**Волна:** 2

## Цель

Что должно заработать, простым языком. Пользователь нажимает кнопку на карточке,
элемент попадает в избранное, кнопка меняет состояние. Повторное нажатие убирает,
а не дублирует; отказ бэка показывается текстом, а не молчанием.

## Из запроса, дословно

> «кнопка избранного на карточке»
> «чтобы было видно, что уже добавлено»

## Разделы PRD и спек

PRD: Истории 1-3, Решения §2, Границы §1.
Спек-дельта `favorites/spec.md`: Requirement «Add to favorites», сценарии 1-4.

## Рамки

Что в задачу входит и что явно нет — соседние задачи, которых она не трогает.

## Подзадачи

1. …
2. …

## Что на выходе

Конкретные артефакты: экран, модель, контракт, тест.

## Definition of Done

- [ ] Нажатие добавляет элемент и меняет состояние кнопки
- [ ] Повторное нажатие убирает, дубля не появляется
- [ ] Состояние переживает переоткрытие экрана
- [ ] Отказ бэка даёт понятный текст, а не падение
- [ ] `./gradlew :feature:favorites:test` зелёный
- [ ] ktlint и detekt чистые

## Тесты

Проверки, привязанные к конкретным Scenario спек-дельты: какой сценарий
каким тестом закрыт и на каком шве он стоит.
```

**Задача, строящая поверхность, называет эталон в критериях приёмки.** Есть `prd_XX_reference.md` — и задача делает экран, форму, страницу, письмо, — значит, минимум один критерий приёмки сформулирован как различие с эталоном, проверяемое глазами: «шапка несёт логотип, поиск и город в одну строку, как в эталоне», а не «шапка сделана». Критерий, описывающий только наличие, закрывается версией, которая работает и выглядит не так, и это проходит и ревью, и приёмку: обе меряют доставленность, а не сходство.

Цена пропуска замерена. Прогон, где эталон был собран в Фазе 2 и лежал на диске всю дорогу, дошёл до приёмки, объявился готовым — и потребовал ещё двенадцати коммитов правки внешнего вида и отдельной сессии на 623 запроса, сделанной руками оркестратора. Эталон был; с ним ничего не сверяли до самого конца. **Сверка, отложенная в конец, не дешевле — она дороже ровно настолько, насколько поздно приходит:** в критерии приёмки различие стоит строки текста, в хвосте прогона — задачи, которую никто не планировал.

Цитаты из запроса в теле задачи стоят около сорока токенов и делают одну важную вещь: удерживают свежий контекст от правдоподобного пересказа того, что было заказано. Пересказ звучит убедительно и расходится с оригиналом ровно настолько, чтобы это заметили в конце.

Путей к файлам и кусков кода в задаче быть не должно — они устаревают быстрее, чем сама задача. Исключение — структура, которую проза передаёт хуже кода: схема, форма типа, конечный автомат. Тогда вставляется только она.

Отчёт по задаче (`prd_XX_rep_NN_<slug>.md`) пишется не здесь, а в Фазе 5, когда работа сделана.

## Гейт G3 — до публикации плана

**Вперёд:** каждое `in-spec`-требование появляется в строке «Требования» хотя бы одной задачи. Требование, не попавшее ни в одну, сделано не будет.

**Первая волна доводит до конца хотя бы один сквозной путь.** Волна, после которой нечего открыть и пройти руками, гейт не проходит — режь заново. Исключение одно: у инициативы нет видимой поверхности вовсе (библиотека, миграция, инструмент), и тогда это записано строкой в плане, а не подразумевается.

**Назад:** каждая задача называет хотя бы одно требование или решение PRD, которое само возводится к требованию. Задача, не возводящаяся ни к чему, — это работа, которую никто не заказывал; её вырезают или привязывают к тому, чему она служит.

**Полнота:** у каждой задачи есть зона и волна, никакие две задачи одной волны не делят зону, и `prd_XX_interfaces.md` уже несёт границы из PRD. Пропущенная волна заставит Фазу 5 угадывать порядок, и угадает она «по одной»; пустые интерфейсы заставят первого субагента угадывать архитектуру.

Потом обнови манифест: `in-spec` → `in-ticket`, с номером задачи.

## Опубликовать план в приборы

Как только файлы задач существуют, **весь список уходит в `state.js` и на дашборд** — не при старте первой задачи и не после её завершения:

```json
{ "id": "04", "title": "Экран со списком избранного", "requirements": ["R02", "R02.1"],
  "blockedBy": ["02"], "wave": 3, "zone": ["features/favorites/list/"], "status": "pending",
  "retries": 0, "repairs": 0, "handoffs": 0 }
```

`status: "pending"`, отметок времени пока нет — они появятся при запуске. Три счётчика заводятся нулями **здесь**: поле, созданное на середине прогона, кто-нибудь увеличит из `undefined`, и получившийся `NaN` не увидит никто, кроме пользователя.

**Работа, идущая при дашборде, который пишет «задачи не нарезаны», — это сломанные приборы**, и ломаются они ровно в тот момент, когда пользователь скорее всего туда посмотрит. Счётчик, волны, блок хода работы и честная шкала прогресса читаются из этого массива; показать то, чего в нём нет, дашборд не может. См. `phases/7-instruments.md`.

## Планировочный отчёт и коммит документов

Когда файлы задач написаны, напиши `<prdRoot>/prd_XX_rep_00_<slug>.md` (`type: report`). Это срез планирования — то, что человек откроет через месяц, когда `state.js` уже ничего не расскажет:

- **Что спланировано** — инициатива в трёх строках, ярус и число задач;
- **Какие файлы произведены** — PRD, спек-дельты по доменам, задачи;
- **Затронутые домены** — какие живые спеки изменятся на архивировании;
- **Открытые места** — каждый `PLACEHOLDER` из PRD, по строке;
- **Отклонения** — всё, что расходится с изначальным запросом, и почему;
- **Дальше** — первая задача.

В vault-режиме дополни `index.md` бандла инициативы (`type: index`) ссылками на PRD, задачи, спек-дельты и этот отчёт: это точка входа во весь бандл, и устаревает она первой. Нет `index.md` — заведи.

Потом коммить документы в репозиторий vault — это первый из трёх коммитов vault за прогон:

```bash
git -C "<vaultRoot>" add "Projects/<project>/<initiative>/" \
  && git -C "<vaultRoot>" commit -m "prd-XX: планирование закончено — <slug>" \
  && git -C "<vaultRoot>" push
```
`<vaultRoot>` — путь из `state.js`, подставляется литералом; команды сцеплены `&&`, чтобы упавший `add` не довёл дело до `push`.

В local-режиме документы лежат в `.prd/` кодового репозитория и уходят в первый же коммит задачи; отдельного коммита документов там нет.

## Как показывать план

Сначала файлы, потом разговор. **План, существующий только в диалоге, планом не является**: пользователь видит сводку по тому, что уже лежит на диске.

**Про параллельность — одна строка и только если она правда**: «Часть задач пойдёт параллельно — 6 задач в 4 волны». Это единственный кусок процесса, который пользователь ощущает напрямую, потому что он меняет время ожидания. Для плана, который представляет собой одну длинную цепочку, эта строка не пишется.

**semi и interview** — один экран, простым языком, без технических деталей, по строке на задачу: что пользователь сможет, когда она закроется. В конце — «План такой, приступаю; если что-то не так, останови». И приступай. Не жди одобрения — ожидание и есть та трата, ради устранения которой всё переписано. **Не обещай отсчёт:** держать паузу ты не умеешь, поэтому «начинаю через минуту» — обещание, которое ты нарушишь на первом же ходу.

`interview` здесь работает как `semi`, и это не упущение: смыслом того режима были вопросы, а не согласование списка задач. Кто хочет спорить о нарезке, говорит «ручной режим».

**full** — тот же экран, но как уведомление. Без паузы.

**manual** — план является гейтом. Показать с технической детализацией, обсудить нарезку и порядок, править по просьбе, дождаться явного «ок». Фаза 5 стартует только по согласованному списку.
